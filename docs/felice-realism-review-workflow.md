# Felice Sailer 2D 真实感评审工作流

> 用途：把 Felice 的专业帆船判断转成可执行的 AI Project 流程。  
> 配套填写表见：[Felice 试玩反馈表](./felice-playtest-feedback-form.md)。

## 1. 项目定位

Sailer 2D 当前是一个能运行、能解释部分物理关系的 V1 原型。Felice 的项目重点不是从零写一个游戏，也不是单纯美化画面，而是证明：

```text
人类专业经验发现真实世界的不一致点，
AI 把这些反馈翻译成小范围代码修改、测试和可试玩原型，
再由人类重新验收。
```

Felice 的角色建议定义为：

```text
Sailing Realism Reviewer / 真实感导演
```

她负责判断“像不像真船”“哪里不像”“应该怎么更像”。AI 和 Eric 负责把这些判断变成开发任务、代码改动、测试和部署。

## 2. 角色分工

| 角色 | 负责什么 | 不主要负责什么 |
|---|---|---|
| Felice | 设计试玩场景、判断真实感、给出专业反馈、验收修改前后差异 | 独自重写物理引擎 |
| 其他帆船同学 | 交叉试玩、补充真实航行感受、指出争议点 | 只给“好玩/不好玩”的泛泛评价 |
| Eric | 控制项目范围、部署、最终取舍、课堂展示组织 | 代替帆船同学判断真实感 |
| AI / Codex | 读取反馈、拆成开发任务、小范围改代码、补测试、生成对比说明 | 替代真实帆船经验 |

## 3. 评审原则

1. 先评真实行为，再评画面。
2. 使用固定测试场景，不自由乱玩后凭感觉总结。
3. 每条反馈必须写清楚“当前表现”和“真实帆船应该怎样”。
4. 每轮只改一个机制，避免不知道哪一处改动产生了效果。
5. 修改后必须让同一组场景重新试玩，形成修改前后对比。
6. 有争议的反馈保留争议，不急着让 AI 强行定论。

## 4. 一轮试玩建议流程

总时长建议 45-70 分钟。

| 时间 | 环节 | 产出 |
|---:|---|---|
| 0-5 分钟 | 说明角色和目标 | 明确 Felice 是真实感导演 |
| 5-10 分钟 | 打开线上入口并熟悉控制 | 所有人知道如何转舵、调帆、压舷、调稳向板 |
| 10-45 分钟 | 逐个完成固定测试场景 | 填写反馈表里的 6 个场景 |
| 45-55 分钟 | 选出最严重的 1-3 个问题 | 得到第一轮开发优先级 |
| 55-70 分钟 | 把反馈翻译成开发任务 | 形成可以交给 AI/Codex 的任务卡 |

## 5. 固定测试场景

| 编号 | 场景 | 重点观察 |
|---:|---|---|
| 1 | 横风航行：调帆太紧/太松 | 船速、帆状态、推力变化是否明显 |
| 2 | 迎风 no-go zone：慢慢转向风眼 | 是否明显掉速、失速、停滞 |
| 3 | Tack 换舷 | 是否有掉速、帆换边、舵效变化 |
| 4 | 顺风航行 | 放帆后的推力和稳定性是否合理 |
| 5 | 稳向板实验：100% vs 0% | 侧滑差异是否足够明显 |
| 6 | 横倾和压舷：强风下压对边/压错边 | heel 和速度变化是否像真实帆船 |

## 6. 反馈到开发任务的翻译规则

| 帆船同学的说法 | 可翻译成的开发方向 |
|---|---|
| 船太容易逆风 | 加强 no-go zone、降低迎风推力、增加 head-to-wind 停滞 |
| 换舷太顺滑 | 加入 tack 速度损失、帆换边延迟、短暂失速 |
| 大舵角不应该还这么快 | 增加 rudder drag，让大舵角降低船速和转向效率 |
| 升稳向板后侧滑不明显 | 提高 centerboard 对 leeway 的影响 |
| 帆太松/太紧反馈不明显 | 强化 sail flow state 对推力、横倾、帆形显示的影响 |
| 横倾不影响速度 | 增加 heel drag 或横倾过大时的效率损失 |
| 看不出为什么变慢 | 在 HUD 中显示帆状态、攻角、no-go / stalled 提示 |

## 7. 第一轮推荐开发任务

建议第一轮只做：

```text
调整迎风和换舷真实感
```

验收标准：

| 标准 | 试玩判断 |
|---|---|
| 船头接近风眼时明显掉速 | 场景 2 能观察到速度下降 |
| 帆进入 luffing 状态时推力很低 | 场景 1 和场景 2 能观察到帆失去驱动力 |
| tack 过程中不能无损转过去 | 场景 3 中换舷会掉速，需要保留动量 |
| 大舵角有额外减速 | 场景 3 中长时间大舵角不再免费转向 |
| HUD 明确显示 attached / luffing / stalled / backwinded | 试玩者不用看代码也能知道帆流状态 |

备注：当前代码内部已有 `sailFlowState`，状态包括 `attached / luffing / stalled / backwinded`。如果界面没有清楚显示，这是第一轮很适合修的教学解释性问题。

## 9. 作业展示结构

Felice 最终展示可以按这个顺序讲：

1. 我不是让 AI 随便做游戏，而是用真实帆船经验审查 AI 原型。
2. 我设计了固定测试场景。
3. 我记录了当前模拟器和真实帆船的差异。
4. 我把反馈交给 AI 转成开发任务。
5. AI 修改代码和测试，我负责验收。
6. 展示一个修改前 vs 修改后的具体例子。
7. 结论：AI 负责快速实现，人负责真实世界判断。
