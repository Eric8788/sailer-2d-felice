# Sailer 新版本启动课教师控场稿

> 用途：给老师把控 80 分钟课堂节奏、信息揭示、学生讨论、AI 使用和 Codex 主线收束。  
> 学生填写用文档见：[Sailer 新版本启动课学生工作纸](./v2-kickoff-student-workbook.md)

## 1. 本节课的教学判断

最推荐的节奏：

```text
开场先展示 2 分钟 V1 作为兴趣钩子，
但不解释、不评审、不展开技术细节。

然后关掉 V1，让学生先从真实帆船出发分析。

等学生已经有了自己的观察和系统抽象，
再正式试玩和评审 V1。
```

原因：

| 方案 | 优点 | 风险 | 结论 |
|---|---|---|---|
| 一开始完整展示 V1 | 兴趣很快起来 | 学生容易被 V1 锚定，只会提“改界面” | 不推荐 |
| 完全不展示 V1，先分析现实 | 思考更独立 | 前 10 分钟可能不够兴奋 | 不推荐单独使用 |
| 先 2 分钟 teaser，再现实分析，再正式评审 | 既有兴趣，又保留独立思考 | 需要老师控制展示深度 | 推荐 |

这节课的核心不是“做出一个功能”，而是让学生经历一次真实的 AI 协作链路：

```text
看见可能性
  -> 回到真实世界
  -> 抽象系统
  -> 审查 AI 原型
  -> 写出需求
  -> 让 AI 执行
  -> 人类验收
```

## 2. 课堂信息揭示原则

不要一开始把完整流程、工具表、prompt 模板全部发给学生看。高中学生看到太多结构，会变成“填表”，思考会变浅。

按阶段揭示：

| 时间 | 展示什么 | 暂时不要展示什么 | 目的 |
|---|---|---|---|
| 开场 | V1 运行画面、今天的大问题 | 详细流程、工具表、完整 prompt | 先让学生想参与 |
| 现实分析前 | 只展示 5 个现实问题 | V1 评审表、AI 工具 | 防止被原型带偏 |
| 系统抽象时 | 5 个系统：环境、船和帆、控制、显示、教学 | 复杂物理公式 | 让学生能拆问题 |
| 正式评审 V1 前 | V1 评审维度 | 学生 AI prompt | 让评审有依据 |
| AI 实践前 | 工具选择表、prompt 模板 | 主线完整技术文档 | 让 AI 帮忙整理，而不是代替思考 |
| 课程最后 | 豆包纪要、主线 Codex 下一步 | 过深代码细节 | 收束成可执行需求 |

你可以一开始只对学生说：

```text
今天会用到三个东西：V1 原型、豆包会议记录、AI 编程工具。
但我们不会马上让 AI 给答案，先用自己的判断把问题想清楚。
```

## 4. 80 分钟课堂节奏

| 时间 | 环节 | 老师动作 | 学生填写 | 关键控制 |
|---|---|---|---|---|
| 00-03 | V1 teaser | 展示 V1 运行，不解释细节 | 第 1 部分兴趣记录 | 只点燃兴趣，不开始评审 |
| 03-08 | 大问题 | 提问 AI 时代人负责什么 | 不急着写 | 把课从“玩游戏”拉回“会创造” |
| 08-20 | 真实帆船分析 | 问为什么动、逆风、侧滑、横倾 | 第 2 部分 | 先不要问 AI |
| 20-30 | 系统抽象 | 把回答收束到 5 个系统 | 第 3 部分 | 不讲复杂公式 |
| 30-42 | 正式试玩 V1 | 带着系统表重新看 V1 | 第 4 部分 | 现在才评审 V1 |
| 42-50 | 新版本定位 | 每组定义自己的项目名和重点 | 第 5 部分 | 明确不必继承 V1 |
| 50-56 | 优先级投票 | 选第一轮最高价值方向 | 第 6 部分 | 每组只选一个重点 |
| 56-63 | Codex 演示 | 展示 Codex 如何读需求、规划 | 观察即可 | 只演示“工程代理怎么思考” |
| 63-73 | 小组 AI 实践 | 释放工具表和 prompt 模板 | 第 7-8 部分 | 让 AI 扩展，不让 AI 替代判断 |
| 73-78 | 豆包纪要 | 生成会议总结，全班校正 | 补充最终卡 | 豆包是草稿，不是结论 |
| 78-80 | Exit ticket | 每组交最终提交卡 | 第 9 部分 | 收束到主线 Codex 需求 |

## 5. 开场 V1 Teaser 怎么演

时间控制在 2-3 分钟。

展示内容：

```text
1. 船能动。
2. 风、水、帆、舵有基本反馈。
3. HUD 或力箭头能看到一些信息。
4. 告诉学生：这是老师周末用 AI 搭出来的参考样机。
```

不要展示：

```text
不要解释全部物理模型。
不要让学生马上评价哪里不真实。
不要打开代码结构。
不要展示完整需求文档。
```

开场话术：

```text
先给大家看 2 分钟，不评价，只感受：
如果一个老师周末用 AI 能做出这个，那我们一群人一起做，会不会能做出更专业、更有教学价值的版本？

但等一下我们不会直接改它。
我们先回到真实帆船，想清楚这个模拟器到底应该模拟什么。
```

## 6. AI 时代人的角色

控制在 5 分钟，不要展开成哲学课。

提问：

```text
如果 AI 可以写代码，人还负责什么？
如果 AI 可以很快做出一个原型，为什么这个原型仍然可能不真实？
一个好项目里，人和 AI 各自应该做什么？
```

收束：

```text
AI 降低的是实现成本，不是思考成本。
人负责观察真实世界、提出好问题、定义价值、判断真假、验收结果。
```

## 7. 真实帆船分析

这一段先不用 AI。

黑板/投屏只放 5 个问题：

```text
帆船为什么会动？
为什么能逆风前进？
为什么会侧滑？
为什么会横倾甚至翻船？
舵、稳向板、人重心分别改变了什么？
```

追问方式：

```text
这个现象是风造成的，还是水造成的？
这个现象是力的问题，还是信息显示的问题？
如果要教会一个初学者，屏幕上必须显示什么？
```

对 VEX 学生的引导：

```text
把帆船想成一个有传感器、控制量、状态反馈的机器人系统。
```

对帆船学生的引导：

```text
你们负责判断：这个说法像不像真实驾驶感受。
```

## 8. 系统抽象

不要拆太细，第一节课只用 5 个系统：

| 系统 | 课堂解释 |
|---|---|
| 环境 | 风、水流、阵风、风向变化 |
| 船和帆 | 船速、航向、帆角、受力、阻力 |
| 控制 | 舵、稳向板、人重心、压舷 |
| 显示 | HUD、箭头、横倾仪、帆形、提示 |
| 教学任务 | 训练目标、评分、回放、挑战 |

你要强调：

```text
我们现在不追求公式完整。
我们先追求：知道有哪些系统，以及系统之间传递什么信息。
```

## 9. 正式试玩和评审 V1

现在再打开 V1。

展示前提醒：

```text
刚才你们已经有自己的真实因素和系统表。
现在我们不是被 V1 带着走，而是用我们的标准审查 V1。
```

评审只问 5 个问题：

```text
V1 最有价值的地方是什么？
V1 最不真实的地方是什么？
V1 最缺少的信息是什么？
V1 最值得借鉴的界面/交互是什么？
V1 最不应该沿用的地方是什么？
```

不要让讨论散成“颜色、按钮、好不好看”。如果学生只提视觉问题，追问：

```text
这个视觉问题背后，是不是某个物理信息没有显示清楚？
```

## 10. 新版本定位和投票

每组可以从零设计，不必叫 V2。

你要重复这句话：

```text
学生版本是试验田，老师的 Codex 主线是课后持续推进的正式产品线。
你们的价值不是统一写同一份代码，而是提出不同角度的高质量判断。
```

投票建议候选方向：

```text
视风和帆攻角
横倾和平衡仪表
舵、稳向板和侧滑
专业 HUD 重设计
训练任务和评分
```

投票收束原则：

```text
今天只选一个第一优先级。
没有被选中的方向不是不要，而是进入后续 backlog。
```

## 11. Codex 演示

这一段控制在 7 分钟以内。

演示目标不是“现场写完整功能”，而是让学生看到工程代理的工作方式：

```text
1. 读文档。
2. 理解目标。
3. 拆任务。
4. 规划文件结构。
5. 说明测试方式。
6. 再开始执行。
```

推荐现场输入：

```text
请根据今天学生讨论出的第一优先级，先不要写代码。
请把它整理成：
1. 功能目标
2. 需要的系统输入和输出
3. 需要显示的 telemetry
4. 最小实现计划
5. 验收标准
```

不要让 Codex 长时间跑实现。课堂中最重要的是让学生理解：

```text
好的 AI 输入来自好的观察和抽象。
```

## 12. 小组 AI 实践

这时再展示工具表和 prompt 模板。

学生可用工具：

| 类型 | 例子 | 适合课堂做什么 |
|---|---|---|
| 会议记录 | 豆包会议、飞书妙记、腾讯会议 AI 纪要 | 记录讨论 |
| 对话 AI | 豆包、DeepSeek、Kimi、通义、ChatGPT、Claude、Gemini | 整理需求、补充遗漏 |
| AI 代码工具 | Trae、Cursor、Windsurf、VS Code + Copilot | 做小原型或项目结构 |
| 工程代理 | Codex、Claude Code、Gemini CLI | 老师主线执行 |

课堂要求：

```text
每组只产出一张最终提交卡。
可以有代码，也可以只有方案。
重点是：真实问题、系统拆分、显示信息、验收标准。
```

## 13. 豆包会议记录怎么用

建议豆包从上课开始录，但不要中途频繁打断。

使用时机：

| 时间 | 用法 |
|---|---|
| 课前 | 开始录音，作为原始记录 |
| 73 分钟 | 让豆包生成结构化总结 |
| 75 分钟 | 全班一起校正错误 |
| 课后 | 你把纪要整理成 Codex 主线需求 |

给豆包的 prompt：

```text
请把本次 AI Club 讨论整理成结构化纪要：
1. 学生提出的真实帆船因素
2. 抽象出的主要系统
3. 对 V1 的评价：有价值、不真实、缺失信息
4. 各组新版本定位
5. 投票选出的第一优先级
6. 可以交给 Codex 执行的需求
7. 需要老师进一步判断的问题
```

校正规则：

```text
删掉空泛描述。
修正帆船术语错误。
保留可执行、可验收的需求。
```

## 14. 课后 Codex 主线

课后你把三类材料交给 Codex：

```text
1. 豆包会议纪要
2. 学生工作纸最终提交卡
3. 你自己的课堂判断
```

主线 prompt 可以这样写：

```text
请阅读 docs/sailer-v2-design.md，以及今天课堂整理出的学生需求。

V1 项目只作为参考，不要直接继续在 V1 上堆功能。
请在当前工作区旁边规划一个新的主线项目。

先不要写代码。
请输出：
1. 第一阶段产品目标
2. 最小系统拆分
3. 物理核心和渲染如何分离
4. 需要输出哪些 telemetry
5. 第一批验收标准
6. 第一轮实现计划
```

## 15. 本节课结束语

```text
今天我们不是在学习“让 AI 替我们完成作业”。
我们是在练习：如何带着真实世界的问题，组织 AI 和人一起创造一个有用的东西。
```

最后提醒：

```text
V1 = 参考样机
学生版本 = 试验田
老师 Codex 主线 = 可持续推进的正式产品线
```
